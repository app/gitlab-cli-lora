## Working process

All project work is plan-driven:

- The plan lives in the temporary file `./tmp/PLAN.md`. For large or complex
  projects the plan may be kept under git control as `docs/PLAN.md` instead.
- If no plan exists, always propose starting by writing one.
- No mutating actions of any kind may start until the user explicitly
  confirms that the plan is ready and work may begin. Until then only
  read-only actions are allowed: reading and gathering data, locally and on
  the internet. Local experiments that require running project code or
  downloading large files from the network are forbidden too.
- The plan always ends with a mandatory `## Done / Next steps` section
  listing the completed points and what to do next. Update it in every
  session, regularly, before returning to wait for the user's prompt.
- When a plan is fully complete, archive it before the next plan takes its
  place: copy it to `./tmp/plan-archive-<YYYYMMDD>.md` (the archiving date;
  append a distinguishing suffix if several plans are archived on the same
  day). Archived plans are reference material and are never edited.
- At the start of a session, always check whether a plan exists. If it does,
  ask the user for permission before continuing work on it.

## Documentation

- Keep the top-level `README.md` at 100 lines or fewer. It is a compact overview
  with a quick start and links, not a reference.
- Put details in short, single-topic files under `docs/`.
- Link every docs page from the README index and cross-link related pages instead
  of duplicating content.
- Update the affected docs in the same change as behavior, configuration or setup.
- Format changed Markdown with `prettier` before finishing:

  ```sh
  prettier --write --prose-wrap preserve --embedded-language-formatting off <paths>
  ```

  This pads Markdown tables so they stay aligned when read in a terminal, and

## Git and Forgejo

- Commits use `GIT_AUTHOR_*` and `GIT_COMMITTER_*` when they are set. Do not
  change the git identity in the repository or in the global config.
- Git over HTTP(S) uses the `forgejo` credential helper, which supplies
  `FORGEJO_TOKEN` for the scheme and host in `FORGEJO_URL` (HTTPS, or HTTP on a
  trusted network), the `github` helper, which supplies `GH_TOKEN` (or
  `GITHUB_TOKEN`) for `https://github.com` only, and the `gitlab` helper, which
  supplies `GITLAB_TOKEN` for `https://gitlab.com` and the host or origin in
  `GITLAB_HOST` (port included; explicit scheme enforced). Git over SSH uses the

  `curl -fsS -H "Authorization: token $FORGEJO_TOKEN" "$FORGEJO_URL/api/v1/version"`.
- Never print, log or commit `FORGEJO_TOKEN` or other credentials.

## Container updates

OpenCode is baked into the image; it cannot update itself inside the container.
Never run `opencode upgrade` or edit `/usr/local/bin/opencode`. Updates are done
on the host with `opencode-podman-build --update`, followed by a container
restart, so ask the user to do that when a newer OpenCode is needed.

## sudo

Passwordless sudo is available inside this container. Use it only to install
software that is missing for the current task.

Allowed:

- `sudo apk add --no-cache <package>` after checking the package name with
  `apk search <package>`.
- Temporary build dependencies via `--virtual`, removed in the same session.

Not allowed:

- Editing, creating, moving or deleting project files through sudo. Container
  root maps to a subuid on the host and would break project file ownership.
  All project changes go through the normal user.
- Running the agent, git, or language tooling as root.
- `apk upgrade`, `apk del` of base packages, or replacing system runtimes
  (system Python, Node).
- Installing language packages with sudo: use project-local tooling, `mise`,
  `uv`, or `npm install`. A global CLI is the exception, not the default.
- Changing `/etc/sudoers*`, `/etc/passwd`, or SSH/GPG configuration.

Rules:

- State the package and the reason before installing, and keep it minimal.
- Runtime installs live in the writable layer and disappear when the container
  exits. If a tool is needed permanently, tell the user so it can be added to
  the Containerfile.
- After installing, verify with `command -v <tool>` and the tool's version.
- Never use sudo to work around a permission error inside the project; fix the
  cause or ask the user.
